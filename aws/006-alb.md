# AWS Application Load Balancer (ALB) & Horizontal Scaling (Beginner's Guide)

When your application starts getting popular, a single virtual server (like a single EC2 instance) will struggle to handle the load. The CPU will max out, the memory will fill up, and users will experience slow response times or connection timeouts. 

To prevent this, you must scale your system. This guide covers the basics of horizontal scaling and how to use the **AWS Application Load Balancer (ALB)** to distribute traffic across multiple servers.

## 1. Vertical vs. Horizontal Scaling

When a server is overloaded, there are two primary ways to scale it:

| Feature | Vertical Scaling (Scale Up) | Horizontal Scaling (Scale Out) |
| :--- | :--- | :--- |
| **Concept** | Make your existing server bigger (add more CPU/RAM). | Add more identical servers of the same size. |
| **Analogy** | Upgrading from an economy car to a heavy-duty cargo truck. | Hiring a fleet of 5 delivery vans instead of 1. |
| **Limits** | **Hard physical limit.** You can only buy a server so big. | **Virtually infinite.** You can add thousands of cheap servers. |
| **Downtime** | Usually requires stopping the server to upgrade hardware. | No downtime. New servers are added while old ones are running. |
| **Resiliency** | **Single Point of Failure.** If the one giant server dies, your app is down. | **High Fault Tolerance.** If 1 of 5 servers dies, the other 4 take the load. |
| **Complexity** | Extremely simple (no code or architectural changes needed). | Higher complexity (requires a coordinator / load balancer). |

## 2. What is a Load Balancer?

If you scale horizontally and run 3 identical EC2 instances to host your website, how does a user's browser know which server to talk to? 

You cannot expect users to manually enter different IP addresses. You need a single door. That single door is a **Load Balancer**.

### The Restaurant Hostess Analogy

Imagine a very popular restaurant with 4 chefs working in the kitchen. 

```
                                  +-----------------------+
                                  |       CUSTOMER        |
                                  +-----------------------+
                                              |
                                     1. Arrives at entrance
                                              v
                                  +-----------------------+
                                  |    HOSTESS (ALB)      |
                                  +-----------------------+
                                    /         |         \
                         2. Routes to free table/chef
                                 /            |            \
                                v             v             v
                           [Chef 1]        [Chef 2]      [Chef 3]
                          (EC2 Inst.)    (EC2 Inst.)   (EC2 Inst.)
```

*   **Without a Hostess:** Customers walk straight into the kitchen, shouting their orders. 10 customers crowd around Chef 1, while Chef 2 and Chef 3 sit idle. The kitchen collapses in chaos.
*   **With a Hostess (The Load Balancer):** Customers wait at the entrance. The Hostess greets them and routes them to tables served by the chef who is currently least busy. The customer only speaks to the Hostess and does not need to know which specific chef is cooking their food.

In software, a **Load Balancer** sits in front of your servers and routes incoming client requests (HTTP/HTTPS) evenly across all healthy backend servers.

## 3. AWS Application Load Balancer (ALB) Deep Dive

AWS offers several types of load balancers. The most popular for web applications is the **Application Load Balancer (ALB)**. 

The ALB operates at **Layer 7** of the OSI model, which means it understands HTTP and HTTPS traffic. This allows it to make routing decisions based on URL paths, query parameters, or HTTP headers.

ALB relies on four core concepts:

### A. Listeners
A **Listener** is a process on the ALB that listens for connection requests from clients. You configure it with a **Port** and **Protocol**.
*   *Example:* You set up an HTTP listener on **Port 80** and an HTTPS listener on **Port 443** to capture web traffic.

### B. Target Groups
A **Target Group** is a logical collection of backend destinations (targets) where you want to route traffic.
*   Targets can be **EC2 Instances**, ECS containers, or AWS Lambda functions.
*   You register your EC2 instances to a specific Target Group (e.g., `production-web-servers`).

### C. Routing Rules
Rules define how the Listener redirects traffic to different Target Groups. Because ALB is Layer 7, you can create advanced rules:
*   **Path-based routing:** Send any request starting with `/api/*` to the `api-servers-tg` target group, and send `/images/*` to the `static-assets-tg` target group.
*   **Host-based routing:** Route traffic for `admin.mywebsite.com` to one target group and `shop.mywebsite.com` to another.

### D. Health Checks
The ALB must ensure it only sends traffic to functioning servers. It does this via **Health Checks**.
*   You configure the ALB to periodically ping a specific path (e.g., `GET /health` or `GET /status`) on each EC2 instance in the Target Group (e.g., every 10 seconds).
*   If an instance fails the health check (e.g., returns a `500 Server Error` or times out), the ALB marks it as **Unhealthy** and temporarily stops sending traffic to it.
*   When the server recovers and passes the health checks again, the ALB automatically resumes sending traffic to it.

## 4. Hands-On CLI Setup Reference

Here are the commands to create and configure an Application Load Balancer using the AWS CLI.

### Step 1: Create a Target Group
Create a target group that expects HTTP traffic on port 80:
```bash
aws elbv2 create-target-group \
    --name my-web-target-group \
    --protocol HTTP \
    --port 80 \
    --vpc-id vpc-0a1b2c3d4e5f6g7h8 \
    --health-check-path /health
```
*(Save the `TargetGroupArn` returned in the JSON response).*

### Step 2: Register EC2 Instances (Targets) to the Group
Register your running EC2 instances into the target group:
```bash
aws elbv2 register-targets \
    --target-group-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/my-web-target-group/abc123xyz \
    --targets Id=i-0abcdef1234567890 Id=i-0123456789abcdef0
```

### Step 3: Create the Application Load Balancer
ALBs must be attached to at least two public subnets in different Availability Zones for high availability:
```bash
aws elbv2 create-load-balancer \
    --name my-web-alb \
    --subnets subnet-0123456789abcdef0 subnet-abcdef01234567890 \
    --security-groups sg-0123456789abcdef0 \
    --type application
```
*(Save the `LoadBalancerArn` and the `DNSName` returned in the response).*

### Step 4: Create a Listener to Route Traffic
Create an HTTP listener on port 80 that forwards all incoming traffic to your Target Group:
```bash
aws elbv2 create-listener \
    --load-balancer-arn arn:aws:elasticloadbalancing:us-east-1:123456789012:loadbalancer/app/my-web-alb/987654321 \
    --protocol HTTP \
    --port 80 \
    --default-actions Type=forward,TargetGroupArn=arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/my-web-target-group/abc123xyz
```

## 5. Production Best Practices Checklist

- [ ] **Multi-AZ Target Distribution:** Deploy your EC2 instances across at least two different Availability Zones (e.g., `us-east-1a` and `us-east-1b`) to protect against data center outages.
- [ ] **Configure Health Check Path:** Do not use `/` (your homepage) for health checks if it loads heavy database content. Create a lightweight `/health` endpoint that returns a simple `200 OK` string instantly.
- [ ] **Strict Security Group Rules:** 
    *   Set the **ALB Security Group** to accept public HTTP (80) and HTTPS (443) traffic from the entire internet (`0.0.0.0/0`).
    *   Set your **EC2 Instances' Security Group** to *only* accept traffic from the ALB's Security Group, blocking direct public access. This prevents attackers from bypassing your load balancer firewall.
- [ ] **SSL/TLS Termination:** Configure HTTPS on your ALB Listener using **AWS Certificate Manager (ACM)**. Let the ALB handle the heavy math of encrypting and decrypting SSL handshakes, passing clean HTTP traffic on Port 80 to your backend servers.
- [ ] **Enable Connection Draining (Deregistration Delay):** Keeps the ALB from immediately severing active user connections when an instance is removed or terminating, allowing active requests to finish gracefully (default is 300 seconds).
