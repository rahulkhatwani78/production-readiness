# AWS Application Load Balancer (ALB) & Horizontal Scaling (Beginner's Guide)

When your application starts getting popular, a single virtual server (like a single EC2 instance) will struggle to handle the load. The CPU will max out, the memory will fill up, and users will experience slow response times or connection timeouts. 

To prevent this, you must scale your system. This guide covers the basics of horizontal scaling and how to use the **AWS Application Load Balancer (ALB)** to distribute traffic across multiple servers.

## 1. Vertical vs. Horizontal Scaling

When a server is overloaded, there are two primary ways to scale it:

| Feature | Vertical Scaling (Scale Up) | Horizontal Scaling (Scale Out) |
| :--- | :--- | :--- |
| **Concept** | Make your existing server bigger (add more CPU/RAM). | Add more identical servers of the same size. |
| **Analogy** | Upgrading from an economy car to a heavy-duty cargo truck. | Hiring a fleet of 5 delivery vans instead of 1. |
| **Limits** | **Hard physical limit.** You can only buy a server so big. | **Virtually infinite.** You can add thousands of cheap servers. |
| **Downtime** | Usually requires stopping the server to upgrade hardware. | No downtime. New servers are added while old ones are running. |
| **Resiliency** | **Single Point of Failure.** If the one giant server dies, your app is down. | **High Fault Tolerance.** If 1 of 5 servers dies, the other 4 take the load. |
| **Complexity** | Extremely simple (no code or architectural changes needed). | Higher complexity (requires a coordinator / load balancer). |

## 2. What is a Load Balancer?

If you scale horizontally and run 3 identical EC2 instances to host your website, how does a user's browser know which server to talk to? 

You cannot expect users to manually enter different IP addresses. You need a single door. That single door is a **Load Balancer**.

### The Restaurant Hostess Analogy

Imagine a very popular restaurant with 4 chefs working in the kitchen. 

```
                                  +-----------------------+
                                  |       CUSTOMER        |
                                  +-----------------------+
                                              |
                                     1. Arrives at entrance
                                              v
                                  +-----------------------+
                                  |    HOSTESS (ALB)      |
                                  +-----------------------+
                                    /         |         \
                         2. Routes to free table/chef
                                 /            |            \
                                v             v             v
                           [Chef 1]        [Chef 2]      [Chef 3]
                          (EC2 Inst.)    (EC2 Inst.)   (EC2 Inst.)
```

*   **Without a Hostess:** Customers walk straight into the kitchen, shouting their orders. 10 customers crowd around Chef 1, while Chef 2 and Chef 3 sit idle. The kitchen collapses in chaos.
*   **With a Hostess (The Load Balancer):** Customers wait at the entrance. The Hostess greets them and routes them to tables served by the chef who is currently least busy. The customer only speaks to the Hostess and does not need to know which specific chef is cooking their food.

## 3. Load Balancer Types: ALB vs. NLB vs. GLB

AWS offers three major types of load balancers:

| Feature | Application Load Balancer (ALB) | Network Load Balancer (NLB) | Gateway Load Balancer (GLB) |
| :--- | :--- | :--- | :--- |
| **Protocol Layer** | Layer 7 (HTTP / HTTPS / gRPC). | Layer 4 (TCP / UDP / TLS). | Layer 3 (IP Packets). |
| **Routing Input** | URL path, host header, query strings, headers. | IP Address & Port. | Direct network routing. |
| **Static IP** | No (resolves via DNS name). | **Yes** (provides Elastic IPs). | No. |
| **Latency** | Low (~10ms). | **Ultra-Low (<1ms).** | Low. |
| **Use Case** | Web applications, REST APIs, Microservices. | Gaming servers, IoT systems, raw TCP sockets. | Third-party virtual security appliances (firewalls). |

## 4. AWS Application Load Balancer (ALB) Deep Dive

ALB operates at **Layer 7** and relies on four core concepts:
*   **Listeners:** A process on the ALB that listens for connection requests from clients on a configured **Port** and **Protocol** (e.g. Port 443 HTTPS).
*   **Target Groups:** A logical collection of backend destinations (targets) where you want to route traffic (e.g. EC2 instances, containers, Lambdas).
*   **Routing Rules:** Defines how the Listener redirects traffic to different Target Groups.
    *   *Path-based routing:* `/api/*` goes to the API group, `/images/*` goes to S3/static group.
    *   *Host-based routing:* `shop.company.com` goes to one group, `admin.company.com` to another.
*   **Health Checks:** The ALB pings a configured path (e.g., `GET /health`) on each target. If a target fails the checks, it is marked **Unhealthy** and traffic routing to it is suspended.

## 5. Step-by-Step Guide: Setting Up ALB in the Console

### Step 1: Create a Target Group
1. Open the **AWS Console** and navigate to the **EC2 Dashboard**.
2. In the left menu, under *Load Balancing*, click **Target Groups**.
3. Click **Create target group**.
4. Configure group parameters:
   * **Choose target type:** Select **Instances**.
   * **Target group name:** `production-tg`
   * **Protocol:** Select `HTTP`, **Port:** `80`.
   * **VPC:** Choose your VPC.
   * **Health checks:** Expand. Set *Health check path* to `/health` (Ensure your Node/Python app actually listens on this path).
5. Click **Next**.
6. Register Targets: Select your running EC2 instances from the list, enter the port (e.g., `80`), and click **Include as pending below**.
7. Click **Create target group**.

### Step 2: Create the Application Load Balancer (ALB)
1. In the left menu, under *Load Balancing*, click **Load Balancers**.
2. Click **Create load balancer**. Under *Application Load Balancer*, click **Create**.
3. Configure settings:
   * **Load balancer name:** `prod-web-alb`
   * **Scheme:** Select **Internet-facing** (allows public traffic).
   * **IP address type:** Select `IPv4`.
   * **Network mapping:** Select your VPC and check at least **two subnets in different Availability Zones** (Required for high availability).
   * **Security groups:** Select a security group that allows inbound traffic on Port 80 and Port 443 from `0.0.0.0/0`.
   * **Listeners and routing:**
     * Listener 1: Protocol `HTTP`, Port `80` -> Forward to Target group `production-tg`.
4. Click **Create load balancer**. *Note: It takes a few minutes to provision.*

## 6. Configuring HTTPS & SSL Certificate Termination

To configure secure HTTPS traffic (Port 443) and auto-redirect HTTP (Port 80) to HTTPS:

### Step 1: Request SSL Certificate via AWS Certificate Manager (ACM)
1. Go to **Certificate Manager (ACM)** in the console.
2. Click **Request certificate** -> Request a public certificate.
3. Enter your domain name (e.g., `api.mycompany.com`) and choose **DNS validation**. Click Request.
4. Add the CNAME records provided by ACM to your DNS registrar (e.g., Route 53 or GoDaddy) to validate ownership. Once validated, status updates to `Issued`.

### Step 2: Add HTTPS Listener to ALB
1. Go back to EC2 -> Load Balancers -> Click your load balancer `prod-web-alb`.
2. Scroll to the **Listeners** tab and click **Add listener**.
3. Configure settings:
   * **Protocol / Port:** HTTPS / `443`
   * **Default actions:** Forward to Target group `production-tg`.
   * **Secure listener settings:** Select **From ACM** and choose your issued domain certificate.
4. Click **Add**.

### Step 3: Redirect HTTP to HTTPS
1. Select the **HTTP:80** listener from the list and click **Edit**.
2. Delete the default "Forward to Target Group" action.
3. Add a new action: **Redirect to URL**.
4. Set:
   * **Protocol:** `HTTPS`
   * **Port:** `443`
   * **Status code:** `301 - Permanent redirect`
5. Click **Save changes**.

## 7. Troubleshooting: Unhealthy Targets Diagnostic Tree

If your targets display a status of `Unhealthy` or remain stuck in `Initial` check status:

```
                  +----------------------------------------------+
                  |           TARGET SHOWS "UNHEALTHY"?          |
                  +----------------------------------------------+
                                         |
                       Does the target security group allow
                       inbound traffic from the ALB group?
                                      /     \
                                   No         Yes
                                  /             \
                  [Add security group rule]      Can the server respond to
                                                 GET /health with 200 OK?
                                                 /                     \
                                               No                       Yes
                                              /                           \
                              Check application logs. Is the        Is health check
                              server running and on correct port?   configured on
                                                                    correct port?
```

### Common Error Root Causes & Fixes:
1.  **Security Group Block:** Your EC2 security group blocks incoming traffic from the ALB.
    *   *Fix:* Edit your EC2 security group rules to allow inbound TCP traffic on your application port (e.g., `3000`) where the source is the security group of the ALB.
2.  **App Misconfiguration:** Your application is running but does not serve a endpoint matching the *Health check path*.
    *   *Fix:* Check app logs. If your health check path is `/health`, add this route in your Node/Express server:
        ```javascript
        app.get('/health', (req, res) => res.status(200).send('OK'));
        ```
3.  **Timeout Limits:** The health check timeout is too short, and the app takes too long to respond.
    *   *Fix:* Increase the timeout setting in the Target Group's health check configuration.

## 8. Production Best Practices Checklist

- [x] **Multi-AZ Target Distribution:** Deploy your EC2 instances across at least two different Availability Zones (e.g., `us-east-1a` and `us-east-1b`) to protect against data center outages.
- [x] **Configure Health Check Path:** Do not use `/` (your homepage) for health checks if it loads heavy database content. Create a lightweight `/health` endpoint that returns a simple `200 OK` string instantly.
- [x] **Strict Security Group Rules:** 
    *   Set the **ALB Security Group** to accept public HTTP (80) and HTTPS (443) traffic from the entire internet (`0.0.0.0/0`).
    *   Set your **EC2 Instances' Security Group** to *only* accept traffic from the ALB's Security Group, blocking direct public access. This prevents attackers from bypassing your load balancer firewall.
- [x] **SSL/TLS Termination:** Configure HTTPS on your ALB Listener using **AWS Certificate Manager (ACM)**. Let the ALB handle the heavy math of encrypting and decrypting SSL handshakes, passing clean HTTP traffic on Port 80 to your backend servers.
- [x] **Enable Connection Draining (Deregistration Delay):** Keeps the ALB from immediately severing active user connections when an instance is removed or terminating, allowing active requests to finish gracefully (default is 300 seconds).
- [x] Configure HTTP to HTTPS redirect rules at the listener level to enforce secure SSL connections.
