# AWS EBS (Elastic Block Store): A Beginner's Guide

When running an application on a virtual server like AWS EC2, the server needs a local hard drive to store the operating system, run code, write log files, and store database files.

**AWS EBS (Elastic Block Store)** provides high-performance block storage volumes (virtual hard drives) designed specifically to be attached to EC2 instances.

## 1. What is AWS EBS? (Layman's Terms)

### The USB Flash Drive Analogy

Imagine you buy a desktop computer tower (this is like an **EC2 Instance**). An **EBS Volume** is like a **USB External SSD** or flash drive.

```
+------------------------+             +------------------------+
|       EC2 INSTANCE     |             |       EBS VOLUME       |
|    (Virtual Computer)  |             |  (External Hard Drive) |
|                        |   cable     |                        |
|  [ Operating System ]  |<===========>|  [ Database Files ]    |
|                        | (Attach/Det)|  [ Application Logs ]  |
+------------------------+             +------------------------+
```

*   **Detachable Persistence:** You plug the USB drive into your computer tower to save files. If the computer tower's processor burns out, you don't lose your files. You simply unplug the USB drive, get a brand-new computer tower, plug the USB drive in, and all your files are immediately available.
*   **Network-Attached:** Unlike physical hard drives inside your laptop, EBS volumes are connected to EC2 instances over a super-fast private network connection behind the scenes.
*   **Availability Zone Bound:** An EBS volume lives in a specific Availability Zone (AZ) (e.g., `us-east-1a`). It can only be plugged into an EC2 instance that is running in that **exact same Availability Zone**.

## 2. Storage Types Comparison: EBS vs. EFS vs. Instance Store

Choosing the right storage architecture is critical for performance and availability:

| Feature | AWS EBS (Elastic Block Store) | AWS EFS (Elastic File System) | Instance Store (Ephemeral) |
| :--- | :--- | :--- | :--- |
| **Type** | Network Block Storage (SSD/HDD). | Network File Storage (Shared). | Direct-attached Physical SSD. |
| **Max Attachments** | 1 instance (except io1/io2 Multi-Attach). | Thousands of instances simultaneously. | 1 instance only. |
| **AZ Dependency** | Locked to 1 Availability Zone. | Shared across multiple AZs. | Locked to the physical host. |
| **Persistence** | Persistent (independent of instance). | Persistent. | **Lost when instance stops or terminates.** |
| **Read/Write Speeds** | Medium to Very High. | Medium (scales with file sizes). | **Extremely Fast (Local connection).** |
| **Use Case** | Boot drives, databases, application log storage. | Shared content directories, web asset shares. | Temporary cache, high-speed swap space. |

## 3. EBS Volume Types

Select the optimal volume type based on performance and budget criteria:

| Volume Type | Technology | Max IOPS | Max Throughput | Best For | Price |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **gp3 (Gen Purpose)** | SSD | 16,000 | 1,000 MB/s | Web servers, test environments, standard databases. | Low |
| **gp2 (Legacy SSD)** | SSD | 16,000 | 250 MB/s | Legacy workloads (gp3 is cheaper and faster). | Medium |
| **io2 (Provisioned)** | SSD | 256,000 | 4,000 MB/s | High-performance production databases (Oracle, MongoDB). | High |
| **st1 (Throughput)** | HDD | 500 | 500 MB/s | Big data analytics, log processing, data warehouses. | Low |
| **sc1 (Cold HDD)** | HDD | 250 | 250 MB/s | Large backup archives, cold storage. | Lowest |

## 4. Step-by-Step Guide: Managing EBS in the AWS Console

### Step 1: Create a Volume
1. Open the **AWS Console** and navigate to the **EC2 Dashboard**.
2. In the left navigation pane, under *Elastic Block Store*, click **Volumes**.
3. Click the orange **Create volume** button.
4. Configure the settings:
   * **Volume type:** Select `gp3`.
   * **Size (GiB):** Enter `20`.
   * **Availability Zone:** Select `us-east-1a` (Ensure this matches the Availability Zone of your running EC2 instance).
5. Click **Create volume**.

### Step 2: Attach the Volume
1. Find your newly created volume in the list (status will show `Available`).
2. Select the checkbox next to the volume, click the **Actions** dropdown, and choose **Attach volume**.
3. Configure target options:
   * **Instance:** Select your running EC2 instance.
   * **Device name:** Keep the default target path (e.g., `/dev/sdf`).
4. Click **Attach volume**. Status will change to `In-use`.

## 5. Step-by-Step Guide: Mounting and Formatting a Volume (Linux Terminal)

After attaching, the Linux OS needs a filesystem to store data.

### Step 1: Identify the Disk Name
Log in to your EC2 instance via SSH and run:
```bash
lsblk
```
You will see your root drive and a new storage device listed. AWS nvme virtualization might display the name as `/dev/nvme1n1` or `/dev/xvdf`.

### Step 2: Check for Existing Data
Ensure the drive is empty before formatting it (formatting wipes out any existing data):
```bash
sudo file -s /dev/nvme1n1
```
*If it returns `/dev/nvme1n1: data`, the drive is empty and safe to format.*

### Step 3: Format the Disk
Format the disk with the standard Linux `ext4` filesystem:
```bash
sudo mkfs -t ext4 /dev/nvme1n1
```

### Step 4: Mount the Volume
Create a target directory and mount the filesystem:
```bash
# Create target directory
sudo mkdir /mnt/app-data
# Mount the disk
sudo mount /dev/nvme1n1 /mnt/app-data
```
Check that the mount is active:
```bash
df -h
```

### Step 5: Configure Auto-Mount on Reboot
By default, the mount disappears if the instance restarts. To make it permanent:
1. Find the unique identifier (UUID) of your partition:
   ```bash
   sudo blkid /dev/nvme1n1
   ```
   *(Copy the UUID string, e.g. `UUID="a1b2c3d4-e5f6-7a8b-9c0d-1e2f3a4b5c6d"`)*.
2. Open the filesystem table in a text editor:
   ```bash
   sudo nano /etc/fstab
   ```
3. Append a new line at the bottom:
   ```text
   UUID=a1b2c3d4-e5f6-7a8b-9c0d-1e2f3a4b5c6d  /mnt/app-data  ext4  defaults,nofail  0  2
   ```
   *Note: `nofail` ensures the server will boot normally even if the volume is detached.*

## 6. Step-by-Step Guide: Resizing an EBS Volume Online

EBS volumes allow you to increase storage capacity and performance (IOPS/throughput) on the fly without stopping your server or causing downtime.

### Step 1: Resize the Volume in AWS
*   **Via CLI:**
    ```bash
    aws ec2 modify-volume --volume-id vol-0123456789abcdef0 --size 50
    ```
*   **Via Console:** Go to EC2 -> Volumes -> Select Volume -> Actions -> Modify Volume. Set size to `50` GiB and click Modify.

### Step 2: Expand the Filesystem inside Linux
Wait for the volume status to display `optimizing` or `completed` (use `lsblk` to verify the partition has resized to 50G). Now tell the OS to use the new space.

1. **Check the filesystem type:**
   ```bash
   df -hT
   ```
2. **If the volume has a partition structure (e.g. `/dev/nvme1n1p1`):**
   ```bash
   sudo growpart /dev/nvme1n1 1
   ```
3. **Resize the filesystem:**
   * **For ext4 filesystems:**
     ```bash
     sudo resize2fs /dev/nvme1n1
     ```
   * **For XFS filesystems:**
     ```bash
     sudo xfs_growfs -d /mnt/app-data
     ```
4. Verify the new size is active:
   ```bash
   df -h
   ```

## 7. Troubleshooting & Common Gotchas

### A. Server Fails to Boot after Detaching Volume
*   **Cause:** You added the mount configuration to `/etc/fstab` but did not add the `nofail` option. When the server reboots and can't find the disk, the kernel halts.
*   **Fix:** Attach the root volume to another temporary recovery EC2 instance, mount it, open `/etc/fstab` in the mount folder, add `nofail` to the line, unmount it, and attach it back as the root drive.

### B. Mounting Fails with `wrong fs type, bad option, bad superblock`
*   **Cause:** The volume was not formatted with a filesystem, or the device path is wrong.
*   **Fix:** Format the device using `sudo mkfs -t ext4 /dev/DEVICE_NAME` (Ensure you check `sudo file -s` first so you don't erase actual data).

## 8. EBS Production Summary Checklist

- [x] Create EBS volumes in the **exact same Availability Zone** as the target EC2 instance.
- [x] Use `gp3` volumes for general workloads to optimize cost and performance.
- [x] Always check for existing files (`sudo file -s /dev/xxx`) before formatting a disk to prevent data loss.
- [x] Configure auto-mounting in `/etc/fstab` using UUIDs so disks remain attached after server reboots.
- [x] Set up automated backup schedules using **AWS Lifecycle Manager (DLM)** to capture snapshots daily/weekly.
- [x] Unmount volumes (`sudo umount /mnt/my-data`) before detaching them to prevent filesystem corruption.
- [x] To transfer an EBS volume's data to a different region or AZ, take a Snapshot, copy it, and restore it in the target location.
- [x] Enable EBS Encryption by default to secure data at rest.
- [x] Use `nofail` parameter inside fstab entries to prevent boot failures if volumes are detached.
