# AWS VPC (Virtual Private Cloud) & Networking: Complete Beginner's Guide

When launching resources in AWS (like databases, load balancers, or EC2 instances), you need control over how they communicate. You don't want your private databases exposed directly to the public internet, but you do want your frontend web servers accessible to everyone. 

**AWS VPC (Virtual Private Cloud)** is the service that lets you build an isolated virtual network inside AWS, giving you total control over IP addresses, subnets, routers, and firewalls.

## 1. IP Addresses & CIDR Notation

Before talking about virtual networks, we must understand how computers address each other.

### A. IP Addresses
An **IP Address** is a unique numerical label (e.g., `192.168.1.15`) assigned to each device connected to a computer network. Think of an IP address as a **physical home mailing address**.

---

### B. CIDR Notation (Classless Inter-Domain Routing)
CIDR is a method used to describe a **block (range) of IP addresses**. It consists of a base IP address followed by a slash `/` and a number (e.g., `10.0.0.0/16`).
*   The number after the slash tells us **how many bits are locked (fixed)** from left to right.
*   **A smaller number after the slash = MORE IP addresses in the block.**
*   **A larger number after the slash = FEWER IP addresses in the block.**

#### IP Ranges Reference Table

| CIDR Block | Locked IP Prefix | Total IP Count | Subnet / Group Level |
| :--- | :--- | :--- | :--- |
| `/16` | `10.0.X.X` | **65,536** | VPC Level (Large block) |
| `/20` | `10.0.0.0` - `10.0.15.255` | **4,096** | Subnet Level (Medium block) |
| `/24` | `10.0.0.X` | **256** | Subnet Level (Standard block) |
| `/28` | `10.0.0.0` - `10.0.0.15` | **16** | Mini Subnet (Small block) |
| `/32` | `10.0.0.1` | **1** | Single host IP |

> [!IMPORTANT]
> **AWS Reserved IP Addresses:** In every subnet you create, AWS automatically reserves **5 IP addresses** for internal routing, DNS, and service management. 
> For example, in a `/24` subnet (256 total IPs), only **251 IPs** are available to be assigned to your EC2 instances. The reserved IPs are: `.0` (Network address), `.1` (VPC Router), `.2` (VPC DNS Server), `.3` (AWS Reserved), and `.255` (Network Broadcast).

## 2. What is a VPC?

### The Gated Community Analogy

By default, the public cloud is like a massive, crowded open city. Anyone can walk around, and there are no walls. A **VPC** is like buying a large plot of land in this city and building a **Gated Community**. 

```
+-----------------------------------------------------------------+
|                        GATED COMMUNITY (VPC)                    |
|                        Range: 10.0.0.0/16                       |
|                                                                 |
|  +---------------------------+     +--------------------------+ |
|  |    Public Park Subnet     |     |   Private Gated Subnet   | |
|  |     Range: 10.0.1.0/24    |     |    Range: 10.0.2.0/24    | |
|  |                           |     |                          | |
|  |     [ Load Balancer ]     |     |    [ Private Database ]  | |
|  |     [ Web Server ]        |     |                          | |
|  +---------------------------+     +--------------------------+ |
|               |                                                 |
|               v                                                 |
|      [ Internet Gateway ] <=====================================+
|          (Main Gate)                     (NAT Gateway)
+-----------------------------------------------------------------+
```

You put up a surrounding fence, establish a guardhouse at the main gate, pave your own internal streets (IP subnets), and set up strict rules about who is allowed in or out of the community.

---

## 3. Subnets (Public vs. Private)

Inside your gated community (VPC), you split your land into separate neighborhoods called **Subnets**.

### A. Public Subnet
*   **Concept:** A neighborhood with a direct, open road connected to the outside world.
*   **What goes here:** Load balancers, public web servers, and jump servers.
*   **How it connects:** It is associated with a route table that directs traffic (`0.0.0.0/0`) to the **Internet Gateway**.

### B. Private Subnet
*   **Concept:** A high-security, hidden neighborhood deep inside the gates. There is no direct road connecting it to the outside world.
*   **What goes here:** Production databases, application backends, and cache servers.
*   **How it connects:** It does *not* have a route to the Internet Gateway. It is completely isolated from direct internet access.

---

## 4. Internet Gateway (IGW) & Route Tables

### A. Internet Gateway (IGW)
The **Internet Gateway** is the **Main Entrance Gate** of your gated community. It connects your VPC to the public internet. Without an IGW, your VPC is completely locked down, and no traffic can enter from or escape to the public internet.

### B. Route Tables
A **Route Table** is a set of rules (a roadmap) that tells network packets where they are allowed to go.
*   Every subnet in a VPC must be associated with a Route Table.
*   **Local Route:** By default, every route table has a local rule (e.g., `10.0.0.0/16 -> Local`). This means any server inside the VPC can talk to any other server inside the VPC.
*   **Default Route (Internet):** To make a subnet public, you add a rule to its Route Table:
    *   `0.0.0.0/0` (Any destination on the internet) -> Send to `Internet Gateway (IGW)`.

## 5. NAT Gateway (Network Address Translation)

### The Mail Forwarding Middleman Analogy

Your database server in the **Private Subnet** needs to connect to the internet to download a critical security patch. However, it does not have a public IP address, and you cannot expose it to the internet because hackers would attack it.

To solve this, we use a **NAT Gateway**.

```
+------------------+          +------------------+          +------------------+
| Private Database | ---1---> |   NAT Gateway    | ---2---> | Public Internet  |
| (Private Subnet) |          | (Public Subnet)  |          | (Downloads patch)|
|                  | <---4--- |                  | <---3--- |                  |
+------------------+          +------------------+          +------------------+
```

1.  **Request Out:** The private database sends the patch download request to the **NAT Gateway** (which lives in the Public Subnet and *does* have a public IP).
2.  **Translate & Send:** The NAT Gateway receives the packet, replaces the database's private IP with its own public IP, and forwards the request to the internet.
3.  **Response In:** The internet site sends the patch files back to the NAT Gateway.
4.  **Forward Back:** The NAT Gateway remembers who asked for it and sends the package back to the private database.

*Result:* The database gets its update, but the public internet never knows the database's private IP. Traffic is strictly **outbound-only**.

## 6. VPC Endpoints (Interface vs. Gateway Endpoints)

If your private resources (like a backend container on Fargate or a database) need to upload files to S3, download container images from ECR, or write logs to CloudWatch, they would normally need to route traffic through the NAT Gateway. This incurs expensive NAT data processing fees.

**VPC Endpoints** solve this by creating a private link between your VPC and supported AWS services, routing traffic inside the AWS private network completely bypassing the public internet and NAT Gateways.

*   **Gateway Endpoints:** A free routing policy update. Best for **S3** and **DynamoDB**. You add a route pointing to the gateway endpoint (`vpce-xxx`) inside your subnet Route Tables.
*   **Interface Endpoints (PrivateLink):** Creates an Elastic Network Interface (ENI) with a private IP address inside your subnet. Traffic to services (like ECR, CloudWatch, Secrets Manager) is routed to this local IP. *Incurs a small hourly fee per interface.*

---

## 7. Connecting VPCs: VPC Peering vs. Transit Gateway

When your application expands and you run multiple VPCs (e.g. one for development, one for production, one for analytics), you need a way to link them:

*   **VPC Peering:** A direct, 1-to-1 connection between two VPCs. High speed, low latency, and free data transfers.
    *   *Limit:* **Not transitive.** If VPC A is peered with VPC B, and VPC B is peered with VPC C, VPC A *cannot* talk to VPC C. You must build a direct peer link between A and C.
*   **Transit Gateway (TGW):** Acts as a **central network hub/router** for all your VPCs, VPN connections, and on-premises offices.
    *   *Benefit:* Simplifies network architecture. You link all VPCs to the TGW, and it handles transit routing among them automatically.

## 8. NACLs vs. Security Groups

AWS provides two distinct layers of security firewalls:

| Feature | Security Group (Instance Level) | Network ACL (Subnet Level) |
| :--- | :--- | :--- |
| **Location** | Sits at the **EC2 Instance** level. | Sits at the **Subnet** boundary level. |
| **Evaluation** | Evaluates rules only for the specific server. | Evaluates rules for *all* servers in the subnet. |
| **State** | **Stateful:** If you allow inbound traffic on Port 80, the return outbound traffic is automatically allowed. | **Stateless:** You must write explicit rules for *both* inbound and outbound traffic. |
| **Rules** | Supports "Allow" rules only. (All else is denied). | Supports "Allow" and "Deny" rules. |
| **Analogy** | **Bouncer at your house door.** If he lets you inside, he remembers you and lets you walk back out. | **Guard at the neighborhood gate.** He checks IDs both when you enter *and* when you leave. |

## 9. Step-by-Step Guide: Designing and Creating a VPC in the Console

### Step 1: Create VPC Wizard
1. Open the **AWS Console** -> Navigate to **VPC**.
2. Click **Create VPC** (orange button).
3. Select **VPC and more** (This creates the subnets, gateways, and route tables automatically in a visual dashboard).
4. Configure settings:
   * **Name tag generation:** `production-vpc`
   * **IPv4 CIDR block:** `10.0.0.0/16`
   * **Number of Availability Zones (AZs):** Select `2` (e.g., us-east-1a and us-east-1b).
   * **Number of Public Subnets:** `2` (One in each AZ, CIDRs: `10.0.0.0/20` and `10.0.16.0/20`).
   * **Number of Private Subnets:** `2` (One in each AZ, CIDRs: `10.0.128.0/20` and `10.0.144.0/20`).
   * **NAT Gateways:** Select **In 1 AZ** (saves cost, or choose *1 per AZ* for production redundancy).
   * **VPC Endpoints:** Select **S3 Gateway** (Free private endpoint for S3 access).
5. Click **Create VPC** at the bottom. Wait for the workflow status blocks to turn green.

## 10. Step-by-Step Guide: Creating a Custom VPC via AWS CLI

### Step 1: Create the VPC
```bash
aws ec2 create-vpc --cidr-block 10.0.0.0/16
```
*(Save the VpcId: `vpc-0123456789abcdef0`).*

### Step 2: Create Subnets
Create one public subnet and one private subnet:
```bash
# Public Subnet
aws ec2 create-subnet \
    --vpc-id vpc-0123456789abcdef0 \
    --cidr-block 10.0.1.0/24 \
    --availability-zone us-east-1a

# Private Subnet
aws ec2 create-subnet \
    --vpc-id vpc-0123456789abcdef0 \
    --cidr-block 10.0.2.0/24 \
    --availability-zone us-east-1a
```

### Step 3: Create and Attach the Internet Gateway (IGW)
```bash
# Create IGW
aws ec2 create-internet-gateway
# Attach to VPC (using returned GatewayId, e.g. igw-098765)
aws ec2 attach-internet-gateway --vpc-id vpc-0123456789abcdef0 --internet-gateway-id igw-098765
```

### Step 4: Configure the Public Routing Table
1. Create a custom route table:
   ```bash
   aws ec2 create-route-table --vpc-id vpc-0123456789abcdef0
   ```
   *(Save RouteTableId: `rtb-1122334455`).*
2. Add route pointing to the Internet Gateway:
   ```bash
   aws ec2 create-route \
       --route-table-id rtb-1122334455 \
       --destination-cidr-block 0.0.0.0/0 \
       --gateway-id igw-098765
   ```
3. Associate Route Table with Public Subnet:
   ```bash
   aws ec2 associate-route-table \
       --subnet-id subnet-public123 \
       --route-table-id rtb-1122334455
   ```

## 11. Troubleshooting: VPC Connectivity Issues

### A. Server in private subnet cannot access the internet (downloads fail)
*   **Causes:**
    *   The route table associated with the private subnet is missing a route to the NAT Gateway.
    *   The NAT Gateway was created in a private subnet instead of a public subnet.
    *   The NAT Gateway does not have an Elastic IP (EIP) attached.
*   **Fixes:**
    *   Add route in the private route table: `0.0.0.0/0` -> Send to `NAT Gateway (nat-xxx)`.
    *   Verify the NAT Gateway sits inside a public subnet (which has a route table directing traffic to `igw-xxx`).

### B. Resources in different subnets cannot communicate
*   **Causes:**
    *   Your Security Group rules block traffic between the instances.
    *   NACL rules explicitly block traffic between the subnet ranges.
*   **Fixes:**
    *   Update Security Groups: Allow inbound TCP traffic from the source security group or CIDR block of the other subnet.
    *   Check NACL inbound and outbound rules for both subnets. Ensure they allow local traffic (`10.0.0.0/16`).

## 12. VPC Production Checklist

- [x] Set your VPC CIDR block (e.g., `10.0.0.0/16`) large enough to handle future growth.
- [x] Deploy subnets in **multiple Availability Zones** (e.g., `us-east-1a`, `us-east-1b`) for high availability.
- [x] Reserve private subnets for all databases and backend application servers.
- [x] Secure your **Jump Server** by restricting SSH access to only your company's VPN or office IP address.
- [x] Use **NAT Gateways** in the public subnet to allow private resources outbound-only internet access.
- [x] Configure stateless **NACLs** as a secondary line of network defense to block malicious IP address ranges.
- [x] Set up S3 and DynamoDB **Gateway Endpoints** to bypass NAT Gateways and save data transfer costs.
- [x] Account for AWS reserving 5 IP addresses per subnet when planning CIDR ranges.
