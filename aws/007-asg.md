# AWS Auto Scaling Group (ASG): Automatic Server Scaling (Beginner's Guide)

When running a production application, traffic fluctuates constantly. In the morning, you might only have 100 users active, but in the afternoon, traffic might spike to 10,000. 

If you configure your Application Load Balancer to route traffic to a fixed number of EC2 instances, you face two risks:
1.  **Under-provisioning (Site Crashes):** If you run too few servers, a sudden traffic spike will overload them, causing your site to go offline.
2.  **Over-provisioning (Wasted Money):** If you run 10 servers all day "just in case" of a spike, you are paying for idle computing power when traffic is low.

**AWS Auto Scaling Group (ASG)** solves this by automatically adjusting the number of EC2 instances running in your backend, scaling them up when traffic rises, and scaling them down when traffic drops.

## 1. What is an Auto Scaling Group? (Layman's Terms)

### The Supermarket Checkout Analogy

Imagine a large local supermarket. 

*   **The Sizing Rules (Scale Out / Scale In):**
    *   In the early morning, there are very few customers. The manager opens only **1 checkout register (Minimum Size)** to save on cashier wages.
    *   In the evening, a rush of shoppers arrives. Lines begin to build. When the queue size at the active register exceeds 5 people (Threshold/Metric), the manager calls over another cashier to open **Register 2 (Scale Out)**.
    *   If traffic keeps growing, they can open up to **5 registers (Maximum Size)**.
    *   Late at night, when the shoppers leave, the manager tells cashiers to close registers and go home, going back down to **1 active register (Scale In)**.
*   **Self-Healing (Auto-Recovery):**
    *   If the cashier working Register 1 suddenly feels sick and walks away, the manager immediately calls a replacement cashier to open Register 1 again so the line keeps moving.

```
                    +------------------------------------+
                    |        AUTO SCALING GROUP          |
                    +------------------------------------+
                      /              |                 \
                     v               v                  v
              [ EC2 Instance ] [ EC2 Instance ] [ EC2 Instance ]
              (Active Register)(Active Register)(Active Register)
                                     ^
                                     |
                                  If dead,
                         ASG automatically replaces it
```

In software, **AWS ASG** performs these exact management duties. It measures metrics (like CPU load or request counts), launches new servers when needed, shuts down idle servers, and automatically replaces crashed servers with fresh ones.

## 2. Core Concepts of ASG

### A. Sizing Parameters
You control the limits of your ASG by setting three configuration bounds:
1.  **Minimum Size:** The absolute lowest number of EC2 instances allowed to run (e.g. `1`).
2.  **Maximum Size:** The absolute limit of EC2 instances the ASG is allowed to launch (e.g. `5` - acts as a budget cap).
3.  **Desired Capacity:** The number of EC2 instances you want running *right now*. ASG will launch or terminate servers to maintain this capacity, dynamically adjusting it based on scaling policies.

```
+-----------------------------------------------------------+
|                    ASG SIZING BOUNDS                      |
|                                                           |
|    [Min: 1] <======== [Desired Capacity: 2] ========> [Max: 5]
|  (Never drop below)     (Current Active Servers)     (Budget Cap) |
+-----------------------------------------------------------+
```

### B. Launch Templates
Before the ASG can launch a new server, it must know *how* to build it. A **Launch Template** is a configuration document that stores all the settings for the EC2 instances to be launched (OS/AMI, instance type, keys, security groups, and bootstrap User Data scripts).

## 3. Scaling Policies Deep Dive

AWS Auto Scaling supports several policies to control group capacity:

### A. Target Tracking Scaling (Thermostat Model)
The easiest and most recommended policy. You select a target metric and set a target value. The ASG handles the scaling calculations automatically:
*   *Example:* "Keep average CPU utilization of the ASG at 50%". 
*   If average CPU hits 70%, ASG adds instances. If it drops to 30%, it removes them.
*   *Supported Predefined Metrics:* Average CPU Utilization, Average Network In/Out, Application Load Balancer Request Count per Target.

### B. Simple and Step Scaling
Scales based on specific CloudWatch alarm thresholds.
*   *Step Scaling Example:*
    *   If CPU is 50% to 70% -> Add 1 instance.
    *   If CPU is 70% to 90% -> Add 2 instances.
    *   If CPU is > 90% -> Add 4 instances.

### C. Scheduled Scaling
Scales based on time and date. Perfect for predictable traffic surges.
*   *Example:* "Scale up to 10 instances every Friday at 5:00 PM for the weekend rush, and scale down to 2 instances on Monday at 9:00 AM".

## 4. Lifecycle Hooks: Graceful Startups and Shutdowns

ASG provides **Lifecycle Hooks** to pause the launch or termination of an instance, allowing you to run custom tasks before the instance joins or leaves the fleet:

```
[ ASG scales in ] ---> [ Instance enters Terminating:Wait ] ---> [ Run tasks (e.g. upload logs, finish requests) ] ---> [ Terminate ]
```

*   **Instance Launching Hook (`InstanceEnteringLifecycle`):** Pauses instance startup to let bootstrap scripts finish installing code, pull dependencies, or run tests before the instance is marked healthy and registered with the ALB.
*   **Instance Terminating Hook (`InstanceTerminatingLifecycle`):** Pauses instance termination (e.g. for 5 minutes) to allow active user requests to complete, back up log files to S3, or gracefully drain database connections before the server is shut down.

## 5. Step-by-Step Guide: Creating an ASG in the Console

### Step 1: Create a Launch Template
1. Open the **AWS Console** -> Go to **EC2 Dashboard**.
2. Under *Instances*, click **Launch Templates** -> **Create launch template**.
3. Set the configuration details:
   * **Launch template name:** `web-api-template`
   * **Template version description:** `v1`
   * **AMI:** Select **Ubuntu Server 22.04 LTS**.
   * **Instance type:** Select `t2.micro` (or `t3.micro`).
   * **Key pair:** Select your SSH key pair.
   * **Security groups:** Select a security group that allows inbound HTTP traffic (Port 80) from your Load Balancer's security group.
   * **User Data** (Expand *Advanced details*): Paste your bootstrap script:
     ```bash
     #!/bin/bash
     apt-get update -y
     apt-get install -y nodejs npm
     # setup code environment...
     ```
4. Click **Create launch template**.

### Step 2: Create the Auto Scaling Group (ASG)
1. In the left menu of the EC2 Dashboard, under *Auto Scaling*, click **Auto Scaling Groups**.
2. Click **Create Auto Scaling group**.
3. Configure wizard settings:
   * **Name:** `prod-web-asg`
   * **Launch template:** Select `web-api-template`. Click Next.
   * **VPC:** Select your VPC.
   * **Availability Zones and subnets:** Select at least **two private subnets** in different AZs (Best practice: keep servers private, access via public ALB). Click Next.
   * **Load balancing:**
     * Select **Attach to an existing load balancer**.
     * Select **Choose from your load balancer target groups** -> Select `production-tg` (Created in ALB guide).
   * **Health checks:**
     * Under *Health check type*, check **ELB** (Enables ASG to replace instances if they fail ALB health checks).
     * Set *Health check grace period* to `300` seconds (Gives instances 5 minutes to launch app before checking health). Click Next.
   * **Group size and scaling policies:**
     * **Desired capacity:** `2`
     * **Minimum capacity:** `1`
     * **Maximum capacity:** `5`
     * **Scaling policies:** Select **Target tracking scaling policy**.
       * *Metric type:* `Average CPU utilization`.
       * *Target value:* `50`.
       * *Instance warmup:* `300` seconds. Click Next.
   * **Notifications / Tags:** Add notifications via SNS or tags (optional).
4. Click **Create Auto Scaling group**.

## 6. Step-by-Step Guide: Managing ASG via AWS CLI

### A. Create Launch Template Configuration File (`template.json`)
```json
{
  "ImageId": "ami-0c7217cdde317cfec",
  "InstanceType": "t2.micro",
  "KeyName": "my-ssh-key",
  "SecurityGroupIds": ["sg-0123456789abcdef0"]
}
```
Register the template:
```bash
aws ec2 create-launch-template \
    --launch-template-name web-api-template \
    --launch-template-data file://template.json
```

### B. Create the Auto Scaling Group
```bash
aws autoscaling create-auto-scaling-group \
    --auto-scaling-group-name prod-web-asg \
    --launch-template LaunchTemplateName=web-api-template,Version='$Latest' \
    --min-size 1 \
    --max-size 5 \
    --desired-capacity 2 \
    --target-group-arns arn:aws:elasticloadbalancing:us-east-1:123456789012:targetgroup/production-tg/abc123xyz \
    --vpc-zone-identifier "subnet-012345,subnet-abcde6" \
    --health-check-type ELB \
    --health-check-grace-period 300
```

### C. Update ASG Sizing Capacity manually
```bash
aws autoscaling update-auto-scaling-group \
    --auto-scaling-group-name prod-web-asg \
    --min-size 2 \
    --max-size 10 \
    --desired-capacity 4
```

## 7. Troubleshooting: ASG Common Failures

### A. Instance Flapping (Infinite Launch/Terminate Cycles)
*   **Symptom:** ASG constantly boots new servers, marks them unhealthy, terminates them, and repeats the cycle.
*   **Causes:**
    *   **Health Check Grace Period is too short:** The server takes 4 minutes to install Node.js and start the app, but your grace period is set to 1 minute. The ASG checks health after 1 minute, finds it unresponsive, and terminates it.
    *   **App Crash on Launch:** The Node.js app fails to boot (e.g. missing environment variables) and exits immediately.
*   **Fixes:**
    *   Increase *Health check grace period* to `300` or `450` seconds.
    *   Log in to one of the booting instances using SSH, or check the instance console output to debug why the boot script or application is crashing.

### B. ASG fails to launch instances (Resource limits)
*   **Symptom:** ASG history shows error: `Launching a new EC2 instance: Status Reason: You have hourly limit for number of instances...`
*   **Cause:** Your AWS account limits (VCPU quotas) have been reached for the selected instance family.
*   **Fix:** Request a quota increase in the AWS Console under *Service Quotas*, or change the instance type in your Launch Template to a family with available quota (e.g., from `t2.micro` to `t3.micro`).

## 8. ASG Production Best Practices Checklist

- [x] **Always Use Launch Templates:** Never use Launch Configurations as they are deprecated.
- [x] **Multi-AZ Availability:** Set your ASG to launch instances across multiple Availability Zones (subnets) to ensure high availability.
- [x] **Configure Health Check Grace Period:** Set a grace period (e.g., 300 seconds) to prevent the ASG from killing newly booted instances before they have had time to finish launching your code and pass their first health checks.
- [x] **Enable ELB Health Checks:** By default, ASG only checks if the EC2 hardware is running. Change the ASG health check type to **ELB** so it replaces servers that fail your Load Balancer's `/health` checks.
- [x] **Set Sane Cooldown Periods:** Ensure your cooldown period allows instances enough time to boot up and start taking load before the ASG checks the metrics again.
- [x] **Set Sane Max Limits:** Always set a conservative maximum capacity limit to prevent run-away scaling (e.g., due to a DDoS attack or an infinite loop bug) from breaking your budget.
- [x] Deploy target tracking scaling policies using the predefined ALB request-count metric to match resource scaling directly with incoming request loads.
